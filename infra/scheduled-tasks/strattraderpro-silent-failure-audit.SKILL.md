Audit the StratTraderPro production platform for "silently green" regressions — failures that look healthy. **Report ONLY if a check fails, or if there is something in the always-report list (see OUTPUT). If everything passes with nothing to note, reply with exactly: `OK — 6/6 checks passed.` and nothing else** (plus the single permitted exception under CLEANUP).

Background (why this task exists): on 2026-07-11 an audit found the entire alerting stack had been inert since deploy — all 17 Grafana alert rules were imported PAUSED, and the `celery-worker` / `celery-beat` Railway services were running gunicorn instead of Celery, so the default task queue had no consumer and no scheduled task had ever run. Nothing detected it, because every failure had disabled its own detector. Each check below guards one of those regressions.

Environment note: everything below is `env="production"` only — the 2026-07-15 OSS pivot renamed the production frontend service and dropped the staging environment, and ADR-109 (2026-08-02) deliberately rightsized the stack to 23→11 alert rules and 7→5 scrape targets. **Those are intended end states, not regressions.** Baselines in this prompt (rule titles, target set, config URL, CHECK 5 bands) were last verified against live production on **2026-09-21**. When an observed value disagrees with a baseline, report the drift as a NOTE with the exact replacement value, even when the check itself passes.

**CHECK 1 — No alert rule is paused.** A paused rule reports `health: ok` because it never evaluates, so a clean bill of health is produced BY the defect.

`GET /api/v1/provisioning/alert-rules` → assert every rule has `isPaused === false`. FAIL if any rule is paused.

Then compare the rule **titles** against this exact set of 11 — a bare count cannot tell "the right 11 rules" from "any 11 rules", so assert the set, not the number:

`AuditIntegrityFailure, BrokerStreamSilent, CeleryQueueDepthHigh, KillSwitchFlattenSlow, KillSwitchTriggered, MetricsBudgetExhausted, MetricsBudgetHigh, MetricsPipelineDown, TargetDown, WebhookErrorRatioCrit, WebhookErrorRatioWarn`

A **missing** title is a FAIL (a rule was deleted). An **extra** title is a NOTE (a rule was added and this baseline needs updating).

Additionally assert the **`StratTraderPro Auth` folder does not exist**, by checking `GET /api/folders` for uid `cfkrwjgh3sxkwa` — **not** by deriving it from the rules array. An empty folder that failed to delete is invisible to a rules-derived check. *(The 11 rules live in the nested subfolder `StratTraderPro/stp-alert-rules.prom.yaml`, uid `alerting-34szz3tqd4u0g`. `GET /api/folders` does not list subfolders — resolve with `GET /api/folders/{uid}` if you assert on folder placement.)*

**CHECK 2 — Every scrape target is up.**

Query `up` → assert every series equals 1, for exactly these **5** jobs, all `env="production"`:

`backend`, `beat`, `worker`, `worker-backtest`, `streams`

FAIL listing any `job`/`env` at 0. (Note: a brief 0 during a Railway redeploy is benign — if exactly one target is down, re-query once after ~90 seconds before reporting.)

Also assert **no `up` series for any other job** and **no `env` value other than `production`**. A `postgres-exporter` or `redis-exporter` series reappearing is a NOTE worth reporting — both services were deleted by ADR-109, so their return means a rebuild or a revert. An `env="staging"` series is likewise a NOTE — staging was retired on 2026-07-15.

**CHECK 3 — The beat→queue→worker loop is alive END-TO-END.** This is the important one. `CELERY_BEAT_SCHEDULE` runs `admin-queue-depths` every 30s, and that task is what WRITES the `celery_queue_depth` gauge. So a fresh `celery_queue_depth` series proves: beat fired → task reached the default `celery` queue → the worker consumed and executed it → the metric was written → the agent scraped it. If any link breaks, the series goes stale/absent.

Query `celery_queue_depth` → assert ≥1 series exists for `env="production"`. Then query `absent(celery_queue_depth{env="production"})` → assert EMPTY. FAIL loudly if absent: it means Celery is broken again (most likely the Railway start command was cleared — see bugs/BUG-011). "FAIL loudly" means record the failure and continue to the remaining checks and to CLEANUP — never abort the run.

Two production queues are expected, `celery` and `backtest`; NOTE (not a failure) if either has no series, since a missing `backtest` series points at `worker-backtest`. A depth of 0 is an *empty* queue, not a stalled one — do not report depth 0 as a problem.

**CHECK 4 — No rule is unhealthy or unexpectedly firing.**

`GET /api/prometheus/grafana/api/v1/rules` → assert every rule has `health === "ok"`. Report any rule in `firing` or `pending` state with its name, folder/group, instance labels, and how long it has been in that state (firing is not automatically a failure — it may be a real alert doing its job — but always report it).

There are **no known-ongoing exceptions** — any firing rule is newsworthy. (The old standing exception, "Auth login success rate < 95%", was a defective `clamp_min` check; ADR-109 deleted that rule along with its folder on 2026-08-02.) Pay particular attention to the dead-man's pair, `MetricsPipelineDown` and `TargetDown` — those two firing means the pipeline itself is down.

**CHECK 5 — Metrics budget.** Grafana bills `active_series x (actual_DPM / included_DPM)`; the free tier includes 1 DPM. Scraping faster than 60s silently doubles the bill.

⚠️ **Evaluate a range, not an instant, and never fail on one sample sitting near 1.0.** With `scrape_interval` correctly at 60s the ratio sits *at* ~1.0 by definition, so instantaneous samples straddle it constantly. Measured over the 30 days to 2026-09-21 (~1,850 active series): median **1.0000**, mean 0.9966, range 0.50–1.25 — i.e. an instant `< 1.0` test would have reported a false FAIL on **65%** of samples, while never once reaching 1.5. A genuine scrape-interval halving drives the *sustained* value toward ~2.0.

On the USAGE datasource:

1. `avg_over_time((grafanacloud_instance_samples_per_second * 60 / grafanacloud_instance_active_series)[3h:5m])` → **FAIL if ≥ 1.3.**
2. `max_over_time((grafanacloud_instance_samples_per_second * 60 / grafanacloud_instance_active_series)[3h:5m])` → report only.
3. `grafanacloud_instance_samples_per_second` and `grafanacloud_instance_active_series` instant values → report as components alongside any FAIL or NOTE.

⛔ **Treat an empty result as FAIL, not as a healthy zero.**

NOTE (not a failure) if the 3h average is ≥ 1.05 or the 3h max is ≥ 1.5 — that is the early-warning band, worth watching but not yet a regression. On FAIL, the cause to check is `scrape_interval` in `infra/grafana-agent/agent.yaml` (bugs/BUG-005-grafana-free-tier-metrics-limit.md). Do NOT use `grafanacloud_org_metrics_billable_series`: it is a billing-period aggregate that keeps climbing even after the cause is fixed.

⚠️ The old `frontend-production-c977f.up.railway.app` host was retired in the 2026-07-15 rename and now returns a Railway edge-level 404 (`"Application not found"` — nothing is bound to that hostname). **Do not use it, and do not "fix" a failure here by switching hosts.**

Assert: (a) the URL actually serves the config JS — FAIL if it 404s, 5xxs, returns an HTML error page, or is empty, because an unreachable check target is a failed check, not a pass, and do NOT substitute a different host to work around it; (b) it contains NO literal `${` anywhere — an unsubstituted var means nginx's `NGINX_ENVSUBST_FILTER` allowlist has drifted from the template and the SPA is being served broken config (this is how frontend Sentry silently never worked); and (c) `release:` is a non-empty 40-char commit SHA, not `''` — an empty release means Sentry sourcemaps cannot resolve and stack traces stay minified. Only non-emptiness is asserted; the value itself changes every deploy. See bugs/BUG-003 and bugs/BUG-004.

Close this tab with `tabs_close_mcp` as soon as its text is captured — do not wait for the CLEANUP step. If the navigate times out or the page fails to load, still close the tab, then record CHECK 6 as failed.
