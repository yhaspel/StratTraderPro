The webhook payload template

The payload template is the JSON body TradingView POSTs to StratTraderPro when your alert fires. It is the entire contract between the two systems: the URL says who and which strategy, the body says what to do.

Where the template lives

Every strategy has its own. You can read it in two places, and they are the same bytes:

  • Strategies → (name) → TradingView payload template — the copy-friendly view, pretty-printed.
  • Strategies → Configure webhook — alongside the URL and the reveal-once secret, which is what you need at the same moment.

Where it goes in TradingView

  1. Open the chart with your Pine strategy applied.
  2. Create an alert on the strategy, not on a bare price condition.
  3. In the alert dialog, open Notifications and tick Webhook URL. Paste the URL from Configure webhook.
  4. Switch to Settings and paste the template into the Message box. The Message box is the request body — nothing else is sent.
  5. Save the alert.
The Message box must contain JSON and nothing else. No leading text, no trailing note, no comments. TradingView sends the box verbatim; any stray character makes it unparseable and the delivery is rejected.

The fields

FieldRequiredWhat it is
strategyyesThe strategy slug. Comes pre-filled; do not change it.
actionyesbuy, sell or exit.
symbolyesThe instrument to trade.
qtyyesQuantity as a number. Your risk profile still has the final say on size.
order_typeyesMKT, LMT, STP or STP_LMT.
sigyesYour webhook secret, verbatim. See below.
idempotency_keyrecommendedA value unique per intended order. A repeat of the same key is answered with {"duplicate": true} and places nothing.
asset_classoptionalSTOCK, ETF, OPTION or FUTURE.

Extra fields are allowed and are stored with the alert, so you can carry your own metadata through.

About sig

sig is a shared secret compared in constant time — it is not an HMAC over the body, so there is nothing to compute. Paste the secret exactly as shown, replacing PASTE_YOUR_SECRET_HERE.

  • The secret is displayed once, when the config is created or rotated. Copy it into a password manager at that moment.
  • Rotating invalidates the previous secret immediately. Any alert still carrying the old value starts failing on the very next fire, so update TradingView in the same sitting.
  • A wrong sig is rejected with SIG_BAD and recorded in the audit log. It is never treated as a duplicate, so a failed attempt during a rotation does not block the corrected retry.

About idempotency_key

TradingView retries. Without an idempotency key, a retried delivery is a second order. The starter template uses TradingView placeholders to build a key that is stable for one signal and different for the next:

"idempotency_key": "tv-{{strategy.order.id}}-{{time}}"

Keep it unique per intended order. A constant string means only the first alert ever trades; a value that changes on every retry defeats the purpose.

TradingView placeholders

Anything in {{ … }} is substituted by TradingView at fire time. Leave those markers exactly as they are — replacing one with a literal value means every alert reports the same thing. Useful ones:

PlaceholderBecomes
{{ticker}}The chart's symbol
{{close}}The bar's closing price
{{time}}The bar time, ISO-8601 UTC
{{strategy.order.action}}buy or sell
{{strategy.order.contracts}}The size the Pine strategy asked for
{{strategy.order.id}}The Pine order identifier

To drive the payload from the script rather than hard-coding it, swap the literals for placeholders — for example "symbol": "{{ticker}}" and "action": "{{strategy.order.action}}". A placeholder that expands to a number still has to be quoted in valid JSON if you leave the quotes in place; the schema accepts qty as a number, so remove the quotes there if you substitute it.

Editing the schema

Each webhook config carries a JSON Schema that the body is validated against after sig is stripped. You can edit it in Configure webhook to require your own fields or tighten enums. Two things are non-negotiable regardless of what your schema says: the five required keys above, and a valid sig.

Use Dry run in the same modal to validate a sample body against your schema before touching TradingView. A dry run places no order.

Reading a rejection

ReasonMeaning
SIG_BADThe sig value does not match the current secret.
SCHEMA_INVALIDThe body parsed but failed the strategy's JSON Schema — usually a missing required key or a value outside an enum.
STRATEGY_DISABLEDDelivery accepted and recorded; the strategy's toggle is off (or it was deleted), so nothing was placed.
NO_BROKER_CONNECTEDNo broker account is linked to your user.
BROKER_NOT_CONNECTEDA broker exists but is not currently connected.
{"duplicate": true}This idempotency_key was already processed. Working as intended.

A rejection returns HTTP 200 on purpose: TradingView treats a non-2xx as a failure and retries, which turns one bad alert into a retry storm. The reason is in the response body and in the audit log.

Testing before you arm it

A disabled strategy still accepts and records deliveries, then drops them with STRATEGY_DISABLED. That is the safe way to prove the URL, the JSON and the secret are all correct: leave the toggle off, fire a test alert from TradingView, confirm the delivery succeeded, and only then enable.
