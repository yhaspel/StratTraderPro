Screening for candidates

A strategy description usually says, in prose, what kind of instrument the strategy wants — "liquid large caps above the 200-day, near their 52-week highs". The Screening panel on a strategy's page makes that executable. You add a small [screen] block to the description; the panel shows the parsed criteria and a Run screen button; pressing it runs one screening call against Financial Modeling Prep (FMP) plus a local pass over daily bars, and returns a ranked candidate list.

Candidates are information only. Nothing is ordered, enabled, watch-listed or backtested as a result of a screen.

Before you start: the instance needs an FMP key

Screening spends the instance's FMP key — there are no per-user keys. If none is configured, the panel says so and the Run button is disabled.

  • Staff users: paste a key at Settings → Data Providers. It is validated against the vendor before it is saved, stored encrypted, and takes effect on every service immediately — no redeploy. The same page's FMP entry is described step by step under Fixing it in Why Market Regime says "no data".
  • Everyone else: ask whoever runs your instance. The panel shows the same message without the link.
  • FRED is irrelevant here. A missing FRED key blocks the market-regime pipeline, never a screen.

One more prerequisite belongs to the operator, not to you: the screener endpoint is not on every FMP plan. This app assumes the premium tier. A key on a plan that excludes the screener produces a failed run with FMP_UNAVAILABLE — see the error table below.

Where the block goes

Inside the strategy's description file — the same DESC file you upload with the Pine script and the webhook template. Anywhere in it: before the prose, after it, or in the middle. Rules:

  • The opening [screen] must start its own line (indenting it is fine). This is what lets you talk about the block in your prose — a sentence like "add a [screen] block here" is a mention, not a second block, and so is a # comment inside the block or a [screen] quoted in a [pine] sample. A block written inline in the middle of a sentence is treated as prose, by both the parser and the description renderer.
  • One block per description. A second one is an error, not a merge.
  • Tags are case-insensitive: [screen], [SCREEN] and [/Screen] all work.
  • At most 4096 bytes and 40 lines between the tags.
  • One key: value per line. Blank lines and lines starting with # are ignored, so you can comment your intent.
  • The block never renders as prose — the description page swallows it entirely, tags and contents.
  • The parse happens on the server only, and errors come back with the line number they occurred on, counted in the whole description.

A worked example

A Minervini-style trend template over liquid US large caps. Copy it into a description as-is and adjust:

[screen]
# Minervini-style trend template, large caps
market_cap: >= 2B
price: 10..1000
volume: >= 1M
sector: Technology
exchange: NASDAQ
above_sma: 50
above_sma: 200
sma_rising: 200
near_52w_high: 25%
limit: 50
[/screen]

Read out loud: companies worth at least $2B, trading between $10 and $1000, with at least a million shares changing hands today, in Technology, listed on NASDAQ — then, of those, the ones trading above both their 50- and 200-day averages, whose 200-day average is rising, and which sit within 25% of their 52-week high. Take at most 50.

Every key

Unknown keys are errors, not warnings: a typo must not silently widen a screen. The Where column matters for quota — "vendor" keys are free (they ride the single screening call), "local" keys cost one daily-bar request per candidate.

KeyAcceptsWhereWhat it means
market_cap>= N, <= N, A..BvendorMarket capitalisation, in dollars.
pricesamevendorLast price.
volumesamevendorCurrent session volume, not average volume — the vendor screens on the live figure and there is deliberately no avg_volume key.
betasamevendorBeta.
dividendsamevendorLast annual dividend, in dollars per share.
sectorone value, up to 64 charactersvendore.g. Technology. Vendor spelling; a list (A|B or A,B) is rejected.
industryone valuevendore.g. Semiconductors.
exchangeone valuevendore.g. NASDAQ.
country2-letter ISO codevendorUS, DE, JP. Case is normalised; anything that is not exactly two letters is an error.
etftrue / falsevendorWhether to screen ETFs instead of companies. Defaults to false, and is sent on every screen either way.
above_sma50 or 200localLast close above the simple moving average of that many sessions. May appear once for 50 and once for 200; repeating the same window is an error.
sma_rising50 or 200localThat average today is higher than it was 20 sessions ago. Same once-per-window rule.
near_52w_high1–100, % optionallocalClose is at least (1 − N/100) of the highest high in the last 252 sessions. 25% means "within 25% of the 52-week high".
min_historywhole days, 1–2000localRequire at least this many daily bars before judging a candidate. It defaults to 260 as soon as the block uses any other local key; setting it on its own is what turns the local pass on for a block that has none.
limit1–100bothHow many candidates the vendor returns and how many get the local pass. Defaults to 50. A value outside the range is clamped, not rejected — limit: 5000 becomes 100.

Notes that catch most authoring mistakes:

  • Numbers take K, M, B, T suffixes (case-insensitive): 2B is 2000000000.
  • Ranges are inclusive only. >=, <= and A..B. A bare > or < is rejected with a message telling you to use the inclusive form, and 5..2 is rejected as inverted.
  • Every key except above_sma and sma_rising may appear once. A repeat is a duplicate-key error.
  • Screens always ask the vendor for actively-traded instruments only; that is not something you can turn off.

What happens when you press Run screen

  1. The vendor keys go out as one screening call and come back as up to limit candidates.
  2. If the block has any local key, each candidate's daily bars are fetched and the SMA, slope and 52-week-high numbers are computed here, not by the vendor. Candidates that fail any local criterion are dropped. A candidate whose history is too short for a window fails that check — it is never passed by default.
  3. Results are ranked deterministically: by distance from the 52-week high (closest first) when near_52w_high is in play, otherwise by market cap, largest first. Ties always break on symbol, so the same inputs give the same order every time.

Runs are snapshots. Each one stores the criteria it parsed and the SHA-256 of the description file at that moment, so editing the description later does not rewrite history — it just means your next run differs from the last. The last 20 of your runs on a strategy are kept; older ones are pruned automatically.

What a screen costs

Be deliberate here — the whole instance shares one key and one quota.

  • A vendor-only block (no above_sma, sma_rising, near_52w_high or min_history) costs exactly one request.
  • A block with any local key costs one request per candidate on top: a 50-candidate derived screen is about 51 requests, and the hard cap of 100 candidates makes 101 the worst case for a single run.
  • FMP's free tier allows roughly 250 requests per day across everything, including the nightly market-regime pipeline. That is about four 50-candidate derived screens in a day, shared by all users.
  • Re-running the same screen re-spends the same requests. The app caches vendor responses, but that cache is a failure fallback — it is read only when the vendor rate-limits us or goes down, so it can serve the last good answer instead of erroring. It is not a 24-hour deduplicator, and pressing Run screen twice in a row costs twice.
  • Two limits keep this bounded: 10 runs per user per hour, and one active run per user per strategy.

Operators: sustained rate-limit and outage behaviour, the metrics to look at, and the client-side cap are all in docs/runbooks/fmp-rate-limit.md. Screener runs are a new burst source on top of the nightly pipeline.

What the errors mean

The first five appear when you press Run screen; nothing is queued. The last two are terminal states of a run that did start.

CodeMeaningWhat to do
FMP_NOT_CONFIGUREDNo FMP key is configured for this instance.Staff: paste one at Settings → Data Providers. Otherwise ask your administrator.
NO_SCREEN_CRITERIAThe description has no [screen] block.Add one — start from the worked example above and re-upload the description.
SCREEN_CRITERIA_INVALIDThe block exists but did not parse.The panel lists each problem with its line number. Fix them and re-upload; the criteria endpoint re-parses on every load, so it doubles as a lint loop.
SCREEN_RUN_ACTIVEA screen for this strategy is already queued or running for you.Wait for it to finish. Runs take seconds to a minute.
RATE_LIMITEDOur limit: more than 10 run-creates in the last hour, by you.Wait. This exists to bound vendor spend, not to punish — screens are cheap to ask for and expensive to serve.
FMP_RATE_LIMITEDThe run started, and the vendor screening call was rate-limited with nothing cached to fall back to.Retry in a few minutes. If it persists, the instance is over its plan's quota — an operator question.
FMP_UNAVAILABLEThe vendor screening call failed and could not be served from cache: an outage, a bad key, or a plan that does not include the screener.Retry once. If it repeats, the operator should confirm the key is valid and on a tier that includes the company screener.

When a result says "degraded"

A degraded run is a finished, honest, incomplete run — not a failure and not a silent truncation. It happens when the vendor rate-limits us or falters partway through the per-candidate bar fetches: rather than pretending the remaining candidates simply did not match, the run stops fetching, finishes with what it has, and tells you exactly what it did not look at.

The counts line spells it out:

CountMeaning
vendor_matchesHow many instruments matched the vendor-side criteria before limit was applied. A big number here with few results means your local criteria are doing the filtering.
enrichedHow many candidates got a full local pass over their daily bars. Zero for a vendor-only block, because none was needed.
returnedHow many rows the table is showing — candidates that passed everything.
insufficient_historyDropped for having fewer daily bars than min_history (260 by default). Recent listings live here. Lower min_history if you want them judged on a shorter series.
skipped_rate_limitedNever examined, because the vendor rate-limited us mid-pass. Re-run later — ideally with a smaller limit.
skipped_unavailableNever examined because of a vendor outage, or skipped individually because that one symbol returned an error (a delisted or unrecognised ticker does this).

The practical reading: if returned looks thin and skipped_rate_limited is large, you did not screen a narrow universe — you screened a partial one. Run it again when the quota recovers before drawing conclusions.
